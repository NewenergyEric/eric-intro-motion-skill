# Product and personal introduction workflow

## Start with evidence and reusable material

Inspect the current site or app, relevant source, existing exports and asset manifests. Record which source revision and export hashes you checked. A completed chat is a useful lead; verify the actual files before treating it as a finished case. List the real user action and visible result for each shot. For a personal introduction, tie the copy to actual work or examples. Do not invent product capabilities, outcomes or medical claims.

Keep a small working manifest: source revision; language; timeline; output sizes; reusable asset paths and hashes; source URLs and licenses; pending checks. Read the changed files and relevant reference sections when resuming. Do not repeatedly load the full source or regenerate artwork already available at sufficient quality.

## Choose shots that explain the action

| Reusable combination | Shot and motion | Useful evidence |
| --- | --- | --- |
| Situation + existing illustration + one concrete line | Bring the problem object into view; let the line settle for reading | Approved copy and original art |
| Filter/search + matching card + selection | Highlight a real choice; move the selected object to its next role | Actual available filters and results |
| Open card + editable field + entered example | Expand the card, reveal explanation, enter a short realistic example | Actual interaction and persistence scope |
| Saved item + library/drawer + confirmation | Move the same item along a target-specific curve into storage | Where and how the app saves it |
| Return state + short CTA + optional QR | Recall the same item and show one next action | Verified destination URL |

These combinations came from inspected source-based productions; they are not a requirement to use five shots. A quiet product may need longer holds; a short profile may need fewer words. Prefer “Write one decision you have already made” to “Unlock limitless productivity.” Keep the user's tone and meaning when shortening.

## Recompose the whole timeline

Plan a row for every scene and columns for square (1080×1080), portrait (1080×1440) and vertical (1080×1920). Specify title position/line breaks, art bounds, card relationships and motion endpoints separately. A reused illustration can remain intact inside a scene; a finished master video cannot substitute for independent layers.

Chinese and English share the story, not necessarily line breaks, font size or label position. Reuse verified translations when available. Watch text baked into illustrations: replace or overlay it only when the source and rights permit it, and inspect the resulting occlusion.

## Iterate and export

1. Render stable reading frames for each scene/language/ratio. Check at phone size and at full resolution. Measure glyph bounds, UI containers, overlaps and missing glyphs. Fix the source instead of hiding or truncating text.
2. Render entrance, action and hold moments plus both sides of each transition. Whole-film native composition includes closing shots and motion paths.
3. Encode the complete timeline, preserve requested audio, check dimensions, frame count, duration, square pixels, codecs and seekability. Decode the entire file. Draw contact sheets from the **encoded MP4** so compression, final audio changes and stale outputs cannot escape review.
4. Play each delivered language/ratio. Decode any QR from compressed frames and verify the link. State separately whether platform upload/phone feed behavior was actually checked.
5. Deliver the videos, posters, editable source, exact dependency lock, manifest, license notices and QA results. Exclude private source, caches, machine paths, credentials and unrelated voice models from public packages.

For Remotion projects that cannot launch their bundled encoder, the inspected case used `renderFrames()` followed by the system FFmpeg. Keep the PNGs under a visual source/assets hash and regenerate only missing or corrupt frames. This is an available fallback, not a reason to replace a working renderer.
